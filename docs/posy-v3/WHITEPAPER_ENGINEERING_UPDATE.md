# Engineering whitepaper update proposal — Proof of Synergy consensus

Publication target: the engineering-aligned Synergy whitepaper, section 3. This text is a cross-repository publication proposal; the external whitepaper source was not overwritten because it is outside the requested `testnet-v3` feature branch.

## Simplified scheduled leadership and chained finality

The proposed fresh-chain PoSy v3 profile separates proposer rotation from voting authority. At Genesis and at each later finalized P3 epoch transition, every active validator independently derives the same immutable leader ring by ranking the frozen validator IDs with a full SHA3-512 schedule hash. The first block extends the canonical Genesis reference rather than a predecessor QC. The schedule does not use stake, Synergy Score, peer-health estimates, or local clocks. Voting authority continues to use the approved frozen validator weights and independent strict count and weight quorums.

Leaders receive fixed ten-block leases. If the scheduled leader fails, a local timeout allows a validator to broadcast a timeout vote but cannot change authority. Only a Timeout Certificate satisfying the same strict count and frozen-weight quorums transfers the remainder of the current lease to the next validator in the immutable ring. A second certified timeout advances to the next ring member. At the next scheduled lease boundary, the original epoch schedule resumes; a temporary failure is not an implicit ban from later leases.

The healthy block path is `PROPOSAL -> VOTE -> QC`. A Quorum Certificate contains canonical context and individually verifiable Aegis ML-DSA-65 signatures; verifiers recompute signer count and frozen weight rather than trusting cached totals. Finality uses a conservative three-certified-block chain: when certified blocks `B0 <- B1 <- B2` consecutively extend one another, `B0` commits. Validators durably preserve their highest and locked QCs, last vote, timeout takeover proof, finalized head, signer journal, and SafetyHalt state across restart.

This simplification does not merge ETDAG with block finality. The fresh Genesis must bind governed ETDAG parameter and fee artifacts before P3 can start. Encrypted transaction admission, certified blind order, reveal gating, and exact protected execution remain separate prerequisites for proposal validity. ETDAG certificates cannot finalize a block or reduce the PoSy quorum.

For the proposed initial five-validator Testnet-v3 topology, a certificate requires four distinct validators and strictly more than two-thirds of frozen voting weight. Five is the first hardware-backed epoch set, not a protocol limit: later finalized epoch transitions may onboard additional validators, rebuild the immutable ring, and derive `floor(2n/3)+1` count quorum from the new frozen set. Single-validator-failure liveness additionally requires that no one validator control one-third or more of that epoch's frozen weight. The profile is not represented as deployed or launch-qualified until its governance, identity, state-agreement, performance, fresh-chain staging, ETDAG, security, and launch gates pass.
