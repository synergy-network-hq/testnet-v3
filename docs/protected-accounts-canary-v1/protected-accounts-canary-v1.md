# Protected accounts, Canary v1 — disabled candidate

Status: **unratified; independent gates below remain open**. Established authority is the October 2026 Address and Identity Specification (AID) §§6.1, 8.3–8.5 and Appendix B, the later CTO scope decisions, and compatible Security Implementation Specification v9.1 controls AI-002, AI-020 and 33/VTE. This candidate narrows the initial release to SNRG transfer and protected D/P device replacement. It does not generalize contract execution or relax EX-01/native PQ authority.

Use [the registry](protected-action-registry-v1.json) and [CDDL](protected-actions-v1.cddl) together. Core implements the action payload decoder and isolated WorldState enrollment, transfer, sponsor commit and ordinary policy replacement. Content framing, sponsored reveal, recovery, consensus scheduling, qualified DKG verification and public admission are **not executable deployment contracts yet**. No implicit switch is allowed.

## Namespace and bytes

The occupied legacy `SYNACT01` tags 0..5 are transfer/native-module/SynQ/SXCP/governance/system; the empty transfer alias is unchanged. Use proposed IDs 28673–28682 in the **APQE signed native u16 field**, not these legacy tags. Never bootstrap this through a generic legacy native module or a field that could pass old signature validation. Legacy unsigned wrappers remain distinguishable and cannot satisfy protected authorization.

[CBOR core deterministic encoding](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.1) applies to admitted original bytes: shortest integer and length, increasing integer keys, fixed definite arrays/maps, no duplicate, omitted or unknown fields, tags, floats, indefinite items or trailing bytes. CDDL expresses the shape under [RFC 8610](https://www.rfc-editor.org/rfc/rfc8610.html). Strict parser and semantic checks remain mandatory. All bstr representations of u256 are exactly 32 bytes BE; Core currently stores balances as u128, so positive transfer amount must fit u128; fee cap comparison uses all 32 bytes. Protected transfer v1 targets an already enrolled 20-byte protected recipient, disallows self-transfer and cannot grant privileges via destination. Legacy treasury disbursement uses the existing authorized envelope once a registry-aware recipient gate exists.

The authenticated signed Genesis selects chain, network, ETDAG processing scope, fee schedule and approved action profile. Native intent carries the Genesis hash as AID table PW13 specifies, not a duplicate native ChainID field. Do not infer EVM ownership chain from the native chain without an explicit Genesis association. Intent ID is unique random 32 bytes and nonzero, separate from nonce; never reuse the ID for changed bytes. Use existing proof-bound finalized state, not client height/time. Valid-until height is inclusive, checked against selected finalized parent; configured validity horizon is pending capacity qualification. Transaction ordering and nonce on the current execution overlay prevent concurrent or replayed spends. Signer proof role, participant, version, algorithm and digest must match current registered records; never accept envelope-supplied keys. Encode proofs in asc role order, with matched full digest and exact 4627-byte ML-DSA-87 signatures.

Ordinary native signing: pure ML-DSA-87 signs `SHA3-512(ASCII("AEGIS/NATIVE-TX/v1") || exact native-intent)` with context `AEGIS.NATIVE.TX.V1`. This same context covers native policy/recovery actions because the registered action ID and payload are signed and their proof rules are disjoint. For a new role PoP, propose the same digest, pure ML-DSA-87 with context `AEGIS.NEW.ROLE.POP.V1`, and compare the envelope to the exact proposed role. PoP does not give current authority.

## Enrollment

Use APQE `protected-enrollment-candidate-v1.cddl` unchanged for the enrollment/policy inner bytes at the pinned APQE revision. The independent APQE fixture is `tests/fixtures/protected-enrollment-verification.json` at the pinned revision; see the [cryptographic profile](crypto-provider-dkg-profile-v1.md) for its qualification limits. Candidate commit is SHA3-256(exact enrollment || fresh private 32-byte CSPRNG salt). Commit is keyed by hash; no revealed account or address reservation. Record inclusion height and consensus time; reveal reads the matching earlier finalized commit from authenticated state (never same block or unfinalized overlay). Require 0 ≤ inclusion time − commit time < 7,200, finalized parent strictly above the commitment block height, inclusion height strictly above parent; also require APQE's signed issued/expiry constraints. No duplicate active commitment or account, substitute identity/policy, stale key, old Genesis, invalid/expired proof, role duplication, or unauthorized provider. AccountIdentifier is last 20 bytes of Keccak-256(X||Y), valid full SEC1 uncompressed point; native output is `synw` plus identical 40-character EIP-55 EVM body.

D/P pure enrollment proofs use SHA3-512(`AEGIS/ACCOUNT-ENROLL/v1` || bytes), context `AEGIS.ACCOUNT.ENROLL.V1`. R possession uses proposed SHA3-512(`AEGIS/RECOVERY-ENROLL/v1` || bytes), `AEGIS.RECOVERY.ENROLL.V1`. Ownership is the separate APQE EIP-712 digest: name SynergyAccountBinding, version 1, approved external uint256 chainId, SHA3-256(`AEGIS/ACCOUNT-DOMAIN/v1` || Genesis) salt, no verifying contract; AccountBinding(bytes32 enrollmentHash,bytes20 accountId,bytes32 nativeGenesisHash,bytes32 nonce,uint64 expiresAt). enrollmentHash uses SHA3-256 over enrollment domain and original bytes. Outer hashing is Keccak-256(0x1901 || domain separator || struct hash); proof uses r||s||parity, low S, exact full point recovery. [EIP-712](https://eips.ethereum.org/EIPS/eip-712) does not supply anti-replay. Only initial ownership is authorized; current D/P remain mandatory. DKG evidence must be independently admitted; a raw 32-byte claim or fixture is insufficient.

Reveal atomically compares prior commit bytes, marks used, installs account policy+ledger state (nonce/epoch 0), and charges the independent sponsor. No pre-registration payment. Candidate record keys in Core use separate commit and account prefixes. Proposed physical retention: expire based on consensus time and remove bounded expired/used records via deterministic priority (expiry, commitment hash) under an approved state budget; ensure active account uniqueness persists indefinitely and any resubmitted record still verifies original enrollment expiry and current sponsor nonce. Budget, pruning cursor and replay load must be qualified before this is valid on network.

## ETDAG, outcomes and observer

Keep the current asynchronous authenticated processing and three-QC PoSy finality. Proposed distinguishing boundary: authenticated admission header exposes network/epoch, ingress selection, payload size class and fee-resource commitment under an approved new content profile; protected intent, payload and proofs are inside encrypted ETDAG content until authorized reveal. Existing single-key outer admission cannot authorize a protected user or reserve its account nonce. Retain terminal processing/idempotency and bind executable result to the exact decrypted bytes and chosen processing context. Wire work still required: select in the governed processing registry a versioned multi-role admission proof that can check resource charging and deduplication without disclosing the intent before reveal. Do not advertise the proposed content framing as current gateway protocol.

Existing `GET /network-profile` serves the signed Genesis/authority; observer validates upstream chain, network, epoch and Genesis. Source method registry binds the existing encrypted processing submission and its admission receipt; `synergy_getProtectedAdmissionReceipt` is not a finality proof. `synergy_getTransaction` resolves finalized transaction receipt/certificate. No protected policy, enrollment, sponsorship or action submission public names are assigned here. Do not create placeholder responses. Once governed, use the existing admitted/processing/finalized/rejected/expired/unavailable distinction and expose the policy at a proof-bound finalized height.

Proposed error precedence: profile/network unavailable → wire/version/limit → action state and time → proof ordering/auth → nonce/fee/reservation → deterministic execution postconditions. Symbolic outcomes: PROTECTED_PROFILE_DISABLED, WRONG_NETWORK, UNKNOWN_PROTECTED_ACTION, UNSUPPORTED_PROTECTED_ACTION_VERSION, NONCANONICAL_PROTECTED_PAYLOAD, PROTECTED_PAYLOAD_SIZE, INVALID_PROTECTED_AMOUNT, INVALID_PROTECTED_ROLE, INVALID_PROTECTED_REFERENCE, INVALID_PROTECTED_REASON, INVALID_PROTECTED_SCHEDULE, ACCOUNT_NOT_ENROLLED, ACCOUNT_ALREADY_ENROLLED, COMMIT_MISSING, COMMIT_IMMATURE, COMMIT_EXPIRED, COMMIT_USED, INVALID_DKG, INVALID_AUTHORIZATION, STALE_POLICY, NONCE_MISMATCH, FEE_CAP_EXCEEDED, INSUFFICIENT_FEE_BALANCE, ACTION_REVERTED. No numeric JSON-RPC assignments are proposed prior to gateway contract integration. Pre-inclusion rejection writes nothing. Included, authenticated deterministic reverts roll back business writes but consume exactly one nonce and the sanctioned fee per AID p78; under-reserved fees or malformed signatures never enter that branch. The isolated transfer fixture tests successful atomic execution and nonmutation on pre-inclusion failure; it does not qualify included revert receipts.
