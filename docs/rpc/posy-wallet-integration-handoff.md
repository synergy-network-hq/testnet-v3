## B. Wallet integration contracts

### Account class and authority

The October 2026 *Address and Identity Technical Manual* v1.0 has SHA-256 `2ff297e775d9e35bcd0472b4276b1c15f02bb72a5a2d853e76040c8276fcc6cc`. Use Part I §§1–4 and Part II PW §§4, 8, and Appendix B. The manual's **DESIGN-SETTLED** rules establish the target architecture. **PROPOSED** assignments and **OPEN — RELEASE BLOCKER** decisions require approval before activation. **LEGACY** and **UNAFFECTED / VERIFY** profiles retain their distinct scope.

- **Personal `synw`.** The `protected_unified_v1` identifier is the last 20 bytes of Ethereum Keccak-256 of the 64 raw coordinates `X || Y` of the validated 65-byte SEC1 aggregate secp256k1 point `04 || X || Y`. Require a finite on-curve point and canonical encoding. Store bytes20, carry unprefixed lowercase hex in the JSON account ID, and display lowercase literal `synw` plus the exact 40-character EIP-55 body. Check the body as written, including valid all-lowercase or all-uppercase checksums. The same body can be rendered after `0x` in an explicit EVM context. Authorization comes from the finalized class and policy under the selected Genesis. The point, checksum and display prefix confer no spending permission. Core's `derive_protected_wallet_address`, `parse_protected_wallet_address` and `decode_address` use the approved APQE address implementation. [Core address crate](../../node-platform/crates/synergy-address/src/lib.rs), [APQE address implementation](https://github.com/synergy-network-hq/APQE/blob/8d2d8fb8a86f07a6b7847d7b1ad8e0cec4a74993/src/apqe/address.rs).
- **Managed `syna`.** `STANDARD_ACCOUNT_PREFIX` uses the SNTS Bech32m profile and the canonical FN-DSA-1024 public identity root. Current ordinary spending uses a separate ML-DSA-87 authorization key and governed `IdentityAuthorizationCarrier`, validated against its finalized binding. The managed-account key/root, participant identity, and approved transaction signature must match. This path covers the engineering treasury and autonomous accounts. Its authorization binding does not create a personal protected policy. `synv` identifies validator records. Proposed multisig prefixes `synm/synu/synl`, executable contract namespaces, SynID aliases and legacy readings remain distinct. Resolve a SynID to a typed address on the selected chain before approval. [SNTS registry and vectors](../../node-platform/crates/synergy-address/standards/), [ordinary admission verifier](../../node-platform/bin/synergy-node/src/services/protected_admission.rs), [identity carrier](../../node-platform/crates/synergy-identity/src/authorization.rs).

### PW13 and enrollment candidate

Current Core and APQE supply exact engineering bytes. Publishable protected consensus actions remain disabled. The [63-item decision register](../protected-accounts-canary-v1/decision-register-v1.tsv) maps canonical sections, new decisions, ownership and coverage. Use the original [registry](../protected-accounts-canary-v1/protected-action-registry-v1.json), [CDDL](../protected-accounts-canary-v1/protected-actions-v1.cddl) and [SHA256SUMS](../protected-accounts-canary-v1/SHA256SUMS), outside live session configuration.

- The proposed PW13 u16 sequence `0x7001–0x700a` is enrollment commit, reveal, transfer, policy schedule/cancel/activate, recovery schedule/veto/cancel/activate. These are candidate assignments, distinct from legacy `SYNACT01` tags 0–5. Registry SHA-256 `aee5e1e0cdc826fc00061d29696adfa291a878cd8689e8d247e49a2cef697bce`, CDDL `a80223355b314d20388c51beb6bb6b9b44d509b8d6282694fcf48bfac3dc3324`.
- PW Table 13 and APQE `CanonicalNativeIntent` define the deterministic CBOR body map 0–10. In order it carries protocol version 1, Genesis bytes32, account bytes20, policy epoch u64, nonce u64, action u16, canonical payload bytes, gas limit u64, max fee exactly 32 big-endian bytes, inclusive valid-until finalized height u64, and nonzero random intent bytes32. Reject nonminimal or reordered encoding, extra fields, indefinite lengths, duplicate keys, tags and trailing bytes. Native pure ML-DSA-87 signs the 64-byte `SHA3-512("AEGIS/NATIVE-TX/v1" || original_body)` with context `AEGIS.NATIVE.TX.V1`. Proofs are role-sorted and bind the version, role, participant, key version, algorithm, exact digest and signature. D and P each use their independent registered keys (2,592-byte public key, 4,627-byte signature). R cannot fill a spending slot. `CanonicalNativeIntent::decode/check_state/digest` and `CandidateProtectedAccounts::verify_spend` enforce the candidate checks. No consumer should substitute ECDSA, caller-supplied authorizing public keys, or the one-key `syna` envelope. [APQE native intent](https://github.com/synergy-network-hq/APQE/blob/8d2d8fb8a86f07a6b7847d7b1ad8e0cec4a74993/src/apqe/native_intent.rs), [Core wire](../../node-platform/bin/synergy-node/src/services/protected_action_wire.rs), [Core state transition](../../node-platform/bin/synergy-node/src/services/protected_accounts.rs).
- Enrollment DCBOR map 0–9 carries version, Genesis, account ID, full point, public policy, DKG transcript commitment, enrollment nonce bytes32, issued time, expiry time and Wallet UUID bytes16. Decode original canonical bytes using the candidate profile. On the decoded object call `verify_candidate_for_selected_chain(provider, &[D, P], &R, &external_chain_policy, &ownership_signature_65, consensus_time)` to obtain a `VerifiedEnrollment`. The provider is typed `PqProvider<Mldsa87>`. This is a stateless candidate check. D/P sign SHA3-512 of `AEGIS/ACCOUNT-ENROLL/v1` concatenated with the intent, context `AEGIS.ACCOUNT.ENROLL.V1`. The R candidate signs SHA3-512 of `AEGIS/RECOVERY-ENROLL/v1` plus intent with `AEGIS.RECOVERY.ENROLL.V1`. The EIP-712 domain is name `SynergyAccountBinding`, version `1`, approved external uint256 chainId, and salt `SHA3-256("AEGIS/ACCOUNT-DOMAIN/v1" || Genesis)`. The type is `AccountBinding(bytes32 enrollmentHash,bytes20 accountId,bytes32 nativeGenesisHash,bytes32 nonce,uint64 expiresAt)`. `enrollmentHash` uses SHA3-256 of the enrollment domain and bytes. Verify the exact 65-byte recoverable low-S signature and compare the recovered full uncompressed point. Initial binding establishes ownership of that point. It grants zero native spending authority. [APQE CDDL](https://github.com/synergy-network-hq/APQE/blob/8d2d8fb8a86f07a6b7847d7b1ad8e0cec4a74993/docs/protected-enrollment-candidate-v1.cddl), [enrollment verifier](https://github.com/synergy-network-hq/APQE/blob/8d2d8fb8a86f07a6b7847d7b1ad8e0cec4a74993/src/apqe/enrollment.rs), [AccountBinding verifier](https://github.com/synergy-network-hq/APQE/blob/8d2d8fb8a86f07a6b7847d7b1ad8e0cec4a74993/src/apqe/account_binding.rs).
- The commit is SHA3-256 of exact enrollment bytes followed by a fresh private 32-byte salt. The candidate requires the finalized parent strictly above the commitment's inclusion height and reveal inclusion after the finalized parent. Time is measured by consensus, with commit age in `[0,7200)` seconds and the signed validity window checked separately. Duplicate, consumed, wrong-Genesis, immature, expired and previously enrolled attempts fail closed. `CandidateProtectedAccounts::prepare_reveal` revalidates the **finalized** commitment and policy preimages and prepares atomic commit consumption, registry creation and zero-balance/nonce-zero ledger insertion. The engineering sponsored-commit and reveal settlement tests do not establish production paid reveal or atomic production dispatch. Pending registration must reconcile against a future proof-bound state read before retry. There are no approved public commit/reveal method names or wire responses to call today. [Candidate spec](../protected-accounts-canary-v1/protected-accounts-canary-v1.md), [Core implementation](../../node-platform/bin/synergy-node/src/services/protected_accounts.rs), [APQE reference registry](https://github.com/synergy-network-hq/APQE/blob/8d2d8fb8a86f07a6b7847d7b1ad8e0cec4a74993/src/apqe/enrollment_registry.rs).
- Initial sponsor pays the commit/reveal fee from its own authorized balance and nonce under the proposed paid profile. Sponsor has no control of the new policy. The user sees enrollment as part of creating a Wallet. Exact quotas, per-action gas, fee/resource liabilities, expiry horizon and paid revert semantics must be frozen and tested before activation. Pre-inclusion refusal consumes no fee or nonce. A valid included action that reverts must consume the fee and nonce with its business writes rolled back. The live ordinary test schedule is 40 nWei/gas and 21,000 gas for transfer (840,000 nWei). Do not apply this fee or a guessed numeric RPC code to PW13 actions. [Fee profile](../protected-accounts-canary-v1/sponsorship-fee-capacity-v1.md), [pending decisions](../protected-accounts-canary-v1/CANARY_RATIFICATION_DECISION_MEMO.md).
- PW §8.5 requires at least 7,200 consensus seconds for D+P routine changes. R plus the surviving D or P may schedule replacement of the lost primary with a minimum delay of 172,800 consensus seconds. Until activation the old D+P policy remains authoritative. D+P can cancel before the deadline, and the replaced role can veto its own recovery before the deadline under the proposed contract. Bind the old and new policy hashes, replacement role, nonce, reason and activation time. Validate the proposed role's possession, atomically advance policy epoch and continue the nonce. Old credentials cannot authorize future actions. Native replacement preserves the account ID and aggregate point. EVM share replacement and R backup/restore are independent APQE/Wallet procedures, with no approved live native recovery RPC, scheduling or automatic activation yet. [Policy state machine](../protected-accounts-canary-v1/policy-recovery-state-machine-v1.md), [APQE and DKG decision record](../protected-accounts-canary-v1/crypto-provider-dkg-profile-v1.md).

For controlled provider testing, use the build report appropriate to that platform and verify its artifact hashes. No ratified protected provider/DKG admission bundle or independent real-device transcript verifier is selected. The DKLs23 engineering candidate has symmetric 2-of-3 external ECDSA ability, including R with either survivor. Its external access structure requires explicit review. Native R remains recovery-only. A simulated DKG commitment gives no threshold assurance. ### ETDAG submission, finality and restart

For the ordinary engineering lane, authenticate a frozen processing context and source finalized record before quoting. The context's authorization height uses the governed offset and key validity. It is not a promised inclusion slot, and must not be patched into an old envelope. Use `ActiveIngressKeys::from_registry` with an independently verified assigned-cluster membership implementation. Authenticate the registry root against the chosen authority, require one active KEM key for every assigned member including any offline member, sort by validator ID, and use `synergy_etdag::certificate_quorum` for the share threshold. The initial 5-member registry therefore produces five capsules and threshold four. Use ML-KEM-1024 and the canonical AES-256-GCM envelope, admission AAD and ordered signed bytes from Core. Native reference is `synergy-keytool prepare-wallet-processing-admission` backed by `author_processing` and `ProcessingAdmissionRequest`. It uses the ordinary transaction signer and carrier. PW13 must ultimately supply a separate negotiated encrypted content and multi-role admission profile. [Client encryption](../../node-platform/crates/synergy-etdag-client/src/), [ordinary authoring](../../node-platform/bin/synergy-keytool/src/wallet.rs), [APQE ETDAG carrier](../../node-platform/crates/synergy-etdag/src/crypto/protected.rs).

Bind user approval to the selected Genesis, sender, recipient, amount, fee/gas caps, authorized nonce, action bytes, policy epoch, expiry and intent ID as applicable. Cache the exact prepared ciphertext/admission bytes and IDs before dispatch. A read can refresh the verified tip, balances, or proof pages without resubmission. An unsent intent may be prepared against a newly authenticated context only if its signed bytes and authorized terms remain valid under the profile, and the old preparation is explicitly invalidated. A change in authorization or signed bytes requires a new approval. A timeout, missing receipt, 503, epoch rollover or restart must keep the sent record pending until independently reconciled. Never blindly re-encrypt, retry, change nonce, or interpret null as zero balance/rejection. The current Wallet native consumer uses a bounded 20-second read deadline. Pace proof reads under server capacity, and keep pending status across app restart.

1. Fetch authenticated successor artifacts from the selected signed origin. `synergy-node authority-successor check-derived-chain CONFIG PROOF` verifies the original chain of bounded (1–16) transitions per input and emits the verified context without activation. For longer histories validate in authenticated successive batches with a proper trusted checkpoint. Revalidate the saved checkpoint and verify each epoch, certified close, verified member/key/weight roots, threshold and exact timeout closure. No fetching authority by advertised height alone.
2. Fetch the complete `finality` document at the receipt height and use the existing native `synergy-node finality-proof verify CONFIG REASSEMBLED_PROOF_JSON` owner. It verifies exactly three contiguous QCs and referenced timeouts under their original epochs, and returns authenticated H, block ID, certificate ID and protected execution root. Reject missing, forged, replayed, wrong-chain and conflicting witnesses.
3. Fetch the matching `block_commitment` pages. Reassemble original base64-decoded bytes, check the first-page digest and length, then recompute SHA3-256 over `SYNERGY_BLOCK_ID_V1 || BE64(byte_length) || exact_bytes`. Bind the verified ID, height and protected execution root. From the authenticated block tuple match the original transaction, receipt, exact fee and execution status. Full World root is SHA3-256 over `SYNERGY_WORLD_STATE_ROOT_V1 || BE64(byte_length) || original_World_JSON`. Match it to the authenticated block preimage, then interpret the typed balance, nonce and policy. Apply the same chain, coordinate and current policy epoch checks to enrollment and recovery. Cross-check pre/post state if the fee or nonce effect is being demonstrated.
4. `world_state` currently provides a bounded complete public World only when every record has an approved disclosure schema. It can refuse valid blocks after pruning, at size/work limits or if an opaque record is present. Core's flat state root does not support a succinct per-account path. A durable transaction/compact block view cannot recover a retired World or a complete receipt inclusion preimage. Introduce an approved proof-bound protected account/receipt provider with explicit retention and failure semantics before making a public verified claim. Unknown/rejected/expired outcomes need authoritative terminal evidence before Wallet replaces the pending intent.
