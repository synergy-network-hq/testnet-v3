# Universal Linux Synergy node package

The deployment master at `Node-Architecture/Linux/Synergy` is generated exclusively
from the canonical native implementation in `01-Core-Protocol/node-platform` by
`tools/linux-node/build_package.py`. Do not hand-edit generated package files.
The same builder, installer, storage and lifecycle apply to every validator.
Twenty role directories are present; only validator is currently implemented.

The sealed `package.json` inventories all software bytes and source content.
A build is a release candidate until its isolated native tests, lifecycle tests,
and migration rehearsal are recorded; it never authorizes live startup or soak.
No credentials, validator identities, private keys or network-specific defaults
are distributed in this package. Select the authenticated Genesis, network
configuration and pinned trust explicitly. Numeric chain ID is a network input.

All Synergy application files live beneath `/opt/Synergy`. The only standard host
registrations are the two systemd units generated by `tools/lifecycle.py`.
The manifest documents required native OS dependencies. NetBird's Unix socket
may have permissive socket bits within the private root-owned0700 `run` directory;
that exact exception does not permit other writable files or directories.

`tools/conformance.py --root /opt/Synergy --expected-manifest /reviewed/package.json
--host` reads software, effective services, configuration schema, storage marker,
and every installed filename. Independent ledger bytes and key values are not
compared, but their locations, types, ownership and permissions are checked.
Unrecognized files, executable runtime payloads, obsolete units, symlinks,
external paths and service overrides fail closed. Configuration fingerprints
normalize only declared identity/network endpoint parameters. Other changes
require explicit review. No entire directory is omitted from inspection.

Fresh installs verify the software footprint before native initialization.
The explicit uncommissioned stage verifies native identity possession, storage
schema, all present configuration fields and paths, and the absence of selected
network inputs or chain history. Commissioned installations require the complete
authenticated public network inputs. Partial network selection fails closed.
Upgrade and startup gates enforce the corresponding installation stage.
Qualification must run the same verifier against the explicitly selected release.
The standalone conformance command never starts services or changes state.

Existing-state upgrades replace sealed software only after PoSy is stopped and
old software/configuration conformance has passed. A durable package-bound intent
allows interrupted replacement to resume using only verified old/new bytes.
Keys, signed public network inputs, signing safety and chain databases remain
untouched. Upgrade starts neither PoSy nor VPN and preserves an already running
owned VPN process; its new executable takes effect only at an operator-controlled
VPN restart. All service controls verify the effective unit's installation owner.
Before startup inspection, SQLite performs its own rollback recovery for an
existing hot journal; journals are never manually removed or ignored. The
standalone conformance command remains read-only and reports recovery needs.
A storage format migration must be rehearsed and separately approved;
never wipe a validator or regenerate identity/genesis to install a correction.
Use `lifecycle.py remove` only under explicit destruction authorization: it checks
attributed OS integrations and VPN retirement before deleting the one root.

Current five-validator network and failed qualification remain STOPPED.
No build, passing fixture or manifest grants permission to restart them.
